# Hosted handbook appearance

Apply this contract to every handbook published in the collection at handbooks.surfaces.systems. The site theme is shared across the gallery and readers. Follow [shared reader implementation](shared-reader-workflow.md) for code ownership, consolidation, and future-edition checks. Keep reusable theme implementation and assets in the skill and invoke them from the editable site build; preserve released PDF and illustration bytes.

## Shared behavior

1. Offer System, Light, and Dark under Appearance. Default to System. Persist an explicit choice between the gallery and readers, synchronize desktop and mobile controls, and follow system changes while System is selected. Keep the reader usable when storage or JavaScript is unavailable.
2. Load the shared theme initialization before styles to avoid a flash of the wrong theme. Reuse the skill's shared theme script and stylesheet; do not copy them into individual books or maintain separate per-book palettes.
3. Give every chapter illustration two authored appearances: the original light/print artwork and a separately rendered dark counterpart with the same subject, composition, and viewpoint. Draw highlights and shadows for dark viewing; never invert the light image or simulate the dark asset with a filter. Keep dark material and recesses dark, with restrained ivory highlights and readable linework. Use a transparent outer background for screen-only dark assets so the page supplies the exact shared `--paper` color (`#191918`). Do not add a rectangular paper plate, vignette, glow, mask, clipping, or blend mode. Preserve the original light artwork and released PDF bytes.
4. Keep technical diagrams separate from chapter artwork. Inline diagrams follow theme ink and paper. Legacy raster diagrams use shared semantic replacements once migrated, with their original assets retained for print. Record any unmigrated raster diagram as an open readability gap. Preserve label contrast and detail. Review colored illustrations and transparent assets in context.
5. Keep browser printing Light and suitable for printing. Offer explicit Daytime version and Late night version PDF downloads under [PDF appearances](pdf-appearances.md). Screen rules must not change fixed PDF files or browser print output.

## Integrating a new reader

The collection integration lives under `site/`; reusable reader modules and browser assets belong in this skill. The site invokes skill-owned modules through `scripts/handbook-toolkit.mjs`; delegating wrappers preserve existing command paths. `scripts/build-site.mjs` finishes with `finalizeSiteThemes` from `scripts/site-theme.mjs`, which discovers the generated HTML pages, injects the shared theme, and validates each page. Do not add a separate list of titles for theme coverage. A new title still needs its reading route, assets, gallery card, release metadata, and publication-front validation.

Use `main#main-content` for handbook content, `.sidebar-meta` for the desktop control, and `.mobile-actions` for the mobile control. Put raster content images inside `figure` elements. Mark chapter engravings with the governing reader's `chapter-figure` or `chapter-art` figure class, or `data-artwork-role="chapter"` for a new class. Diagrams can use the full content width. Avoid inline filters, masks, clipping, blending, and background overrides on images or their ancestors, including figures and picture wrappers. Other publishing implementations must provide equivalent behavior and validation.

Each book owns an `artwork-pairs.json` manifest beside its approved reader package. Each entry records the original reader asset and hash, a distinct screen-only dark PNG and hash, pixel dimensions, composition and style references, the full prompt, generation provenance, and visual acceptance. Keep dark assets under `assets/chapter-art/dark/`. The collection build verifies the manifest against the approved light package and installs the pairs into generated readers; do not rewrite the approved package to add a screen appearance.

The selected dark style reference is `assets/design-system/dark-illustration-reference.png` in this toolkit. Use it for shading and linework while using each chapter's original light image for subject and composition. The reference itself has an opaque background; final dark screen assets require genuine alpha transparency, recorded as `outerBackground: "transparent"`, and visual acceptance on the shared page background.

The shared build inserts a `picture` source marked `data-dark-artwork`, with `media="screen and (prefers-color-scheme: dark)"`, before the original light sources and image. Shared `theme.js` sets its media to `screen` for an explicit Dark choice and `not all` for Light. Without JavaScript the native media follows System. Screen-only source selection falls back to the original light image for print, including printing from Dark. The build must reject chapter artwork without a distinct dark source. Do not maintain a separate list of book titles for appearance coverage.

Run `npm --prefix site run validate:front-pages` from the collection repository after rebuilding. The theme checks must discover all output pages and exercise a future reader on an arbitrary route. Missing shared assets, misplaced or missing controls, images outside the shared figure structure, and local image overrides must fail the build. Structural checks establish coverage; rendered checks establish appearance.

## Before publication

1. Verify the new title on desktop and mobile in System, Light, and Dark. Check navigation between gallery and reader, persistence of the chosen appearance, and the desktop and mobile controls.
2. Inspect every chapter opener and raster diagram in light and dark modes. Confirm the correct light/dark asset loads, naturally drawn shading, readable labels, intact silhouettes, and no horizontal overflow. Check that transparent dark margins reveal the exact page background without a rectangular plate or pale fringe. Inspect transparent or colored assets as well as monochrome engravings.
3. Compare computed image and ancestor filters, masks, clipping, blending, background, and dimensions with the shared reader treatment. Reject a local stylesheet that overrides the shared appearance, even when the markup check passes.
4. Check browser printing from a dark reader and verify the exact PDF download checksum. Browser printing must remain Light; verify each fixed PDF appearance against its own approved checksum. Record screenshots and results for the candidate and deployed output before claiming publication is complete.

A missing theme surface, unreadable diagram, negative-looking engraving, or dark browser print output fails the hosted publication gate. Repair the shared source when the defect affects multiple titles and rerun the affected checks.
