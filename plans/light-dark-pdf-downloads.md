1. Add a skill-owned PDF appearance token file and adapters for CSS and ReportLab. Retain the existing Light values and approved type metrics. 2. Preserve fonts, sizes, line heights, margins, illustration slots, page breaks, table widths, and diagram geometry between a Light/Dark pair. Theme changes affect colors and selected assets. Apply tokens to headings, body, links, tables, code, callouts, worksheet cells, footers, rules, and diagrams. Record any book-specific geometry in configuration. No whole-page inversion, pixel recoloring of the light PDF, blend modes, or filter-based illustrations.
3. Paint an opaque full-page background behind every Dark page, including the cover, contents, back matter, and margins. In Chromium, use an explicit `data-pdf-theme` profile under print media and retain `printBackground: true`. In ReportLab, paint the page before any content in every page template. Theme the Engineering overlay separately so it cannot introduce dark-on-dark text or white patches.
4. Reuse the 36 existing separately authored Dark illustrations only after verifying their hashes, composition, dimensions, and PDF placement resolution. Their transparent screen margins are valid source inputs, not PDF-ready assets. A shared normalizer composites each onto the exact PDF paper token, records the transform, and freezes an opaque RGB output without `/Mask` or `/SMask`. Light artwork remains on white. Do not overwrite selected originals or current screen assets. A color background plate must not be converted to grayscale after composition.
5. Register PDF derivatives in each book's artwork manifest or a versioned companion manifest, bound to the existing artwork-pair entry and hashes. Require at least 240 effective PPI, preferably 300, at the actual placement. Check matching optical framing and no pale fringes, rectangles of a different charcoal, or reversed shadows. If an existing Dark input fails, author a separate replacement through the illustration workflow within the later approved implementation scope; do not silently alter or invert Light art.
6. Keep diagram labels, node/edge relationships, feedback, notes, numbering, and reading equivalents with the book. Move reusable SVG/ReportLab rendering into the skill. Generate both PDF appearances from the same definitions and fixed print geometry. Prefer vector output with real text; any required raster fallback must be theme-specific, opaque, and resolution-checked. Audit every diagram placement, including repeated diagrams and unmapped legacy assets. A dark page with a light diagram panel fails.
7. Keep browser printing Light, even from a Dark reader. A downloaded Dark PDF is a fixed dark document: printing it consumes dark background ink and a viewer's background suppression may make pale text unreadable. The cover's short printing guidance directs readers to Light; do not change the Dark file when someone prints it.

## Versioning and compatibility

Recommend an additive PDF appearance revision for each current content edition. Keep content versions at Engineering 1.4.0 and Evaluation/Consulting 1.0.0. Record `appearanceRevision: 1` and a separate artifact approval date. Adding a Dark companion does not rewrite the edition's Light PDF, its publication date, frozen reader package, release manifest, or hash ledger. Amend the edition policy explicitly to distinguish an added format from replacement of an existing artifact.

For each current book, add a book-owned `pdf-variants.json` sidecar keyed to its approved content edition. It points Daytime to the original light file and adds Late night as `<slug>-v<version>-<edition-date>-late-night-r1.pdf`. The new Late night canonical route is `/<slug>/editions/v<version>/<filename>`. Keep every existing Light route and stored filename. Set the Daytime link's `download` filename to `<slug>-v<version>-<edition-date>-daytime-r1.pdf` so readers receive the new name without changing the hosted URL or artifact bytes. Verify that saved filename in the browser checks; a new hosted alias is unnecessary for the initial migration.

New editions use `<slug>-v<version>-<edition-date>-daytime-r1.pdf` and `...-late-night-r1.pdf`. For example, an AI Evaluation Late night companion would be `ai-evaluation-v1.0.0-2026-10-01-late-night-r1.pdf`. An appearance-only replacement advances `r1` to `r2` at a new immutable URL and retains the prior artifact. A replacement of the edition's distributed content follows the skill's patch/minor/major policy. The version names belong in filenames and metadata, not added cover paragraphs that alter pagination.

Use a versioned manifest schema with:

1. Content identity: book ID, title, content version/date, canonical source revision and hashes, approved previous edition, and content comparison/changelog decision.
2. Variant identity: internal theme (`light` or `dark`), display name (`Daytime version` or `Late night version`), appearance revision/date, local path, absolute public URL, saved download filename, SHA-256, byte size, measured page count, page-map path/hash, and approval status for each file. Shared rendering supplies the approved display names so books do not maintain competing labels.
3. Build provenance: toolkit revision, appearance token hash, renderer/toolchain versions, command/configuration, font hashes, semantic diagram hashes, artwork original/normalized hashes and transforms, and finalizer version.
4. Proof: structural report, exact text diff, per-page comparison, navigation/outline/link results, Poppler and PDFKit proof paths, accessibility results/limitations, and approval of the exact artifact hashes.

Retain legacy `pdf`, `sha256`, and `pages` as Light compatibility fields for old consumers. The resolver accepts the existing single-PDF manifest as Light-only, validates sidecars against that identity, and rejects missing, stale, unapproved, duplicated, or mixed-edition variants. New manifests must include both themes. Never alter a released manifest to pretend that an earlier build generated Dark.

Replace the fixed edition allowlist with a collection approval registry that pins each content package and variant manifest by hash. Catalog configuration and the registry must agree. Ordinary discovery, a new book folder, or a candidate manifest cannot confer publication authority. Preserve the current three approvals and leave all draft titles excluded.

Add an explicit retained-release inventory to the site build. Copy historical files and aliases during every clean rebuild, validate their hashes, then add approved variants. Frozen reader packages gain download controls only through the shared assembly step, as they already gain hosted artwork and themes. Keep their source bytes intact. Old public edition pages may gain the approved companion links while retaining their content identity and original Light URLs.

If Dark changes only appearance, compare its substantive text to the approved Light and record unchanged content. Add no new reader-facing changelog page or navigation entry. Preserve any changelog already belonging to the released edition. If wording or sequence changes, stop the companion migration and propose a content edition with the required change ledger and changelog.
